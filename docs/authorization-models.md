# Модели авторизации доступа

Аутентификация отвечает на вопрос «кто ты», авторизация — «что тебе можно».

| Модель | Принцип | Сильная сторона | Слабая сторона |
|---|---|---|---|
| DAC | Владелец ресурса сам назначает права | Простота для единоличного владения | Не масштабируется, нет центрального контроля |
| RBAC | Права группируются в роли, роли — пользователям | Понятна администратору, стандарт де-факто | «Взрыв ролей» при мелких исключениях |
| ABAC | Решение по атрибутам субъекта/объекта/контекста | Гибкие контекстные политики (время, отдел и т.п.) | Сложность написания и аудита политик |
| ReBAC | Право выводится из графа отношений | Хорошо описывает вложенные ресурсы (папки, документы) | Сложная реализация (Google Zanzibar, SpiceDB) |
| Делегированная (OAuth 2.0) | Пользователь выдаёт токен с ограниченным scope | Доступ третьим приложениям без передачи пароля | Сама по себе не решает, *что* можно делать — это на стороне ресурс-сервера |

На практике модели комбинируют: RBAC для базовых ролей внутри портала и
ABAC-политики для контекстных проверок на уровне отдельных микросервисов —
это стандартная практика при построении сложных систем.
