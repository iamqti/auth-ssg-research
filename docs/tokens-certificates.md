# Токены и сертификаты

## Аутентификация на основе токенов

После проверки логина/пароля сервер выдаёт токен (чаще — JWT), который при
последующих запросах заменяет пароль: сервер проверяет подпись и срок
действия. Подход разделяет аутентификацию и авторизацию и упрощает
масштабирование — приложению не нужно хранить состояние сессии.

Риски: кража токена (например, через XSS при хранении в `localStorage`),
replay-атака повторно использованным токеном, отсутствие встроенного
централизованного отзыва у JWT. Поэтому используют короткий TTL с
refresh-токеном, флаги `Secure`/`HttpOnly` для куки и короткоживущие ключи
подписи.

## Аутентификация на основе сертификатов (PKI)

Каждый пользователь или устройство владеет сертификатом X.509, подписанным
удостоверяющим центром. При установке TLS сервер и/или клиент предъявляют
сертификат и доказывают владение приватным ключом — достигается взаимная
аутентификация. Способ применяется в корпоративных VPN, Windows-доменах и
государственных системах.

Главный риск — компрометация приватного ключа: если он украден вместе с
сертификатом, подделать аутентификацию тривиально. Требуется надёжное
хранение ключа (смарт-карта, TPM) и оперативная проверка отзыва (CRL/OCSP).

## mTLS и JWT для межсервисного взаимодействия

| Подход | Где уместен | Главный риск |
|---|---|---|
| API key / HMAC | Простая интеграция, низкая стоимость | Статичный секрет, сложно ротировать |
| mTLS | Строгая взаимная проверка между сервисами | Нужна собственная PKI и ротация сертификатов |
| JWT + OAuth 2.0 Client Credentials | Микросервисы с центральным IdP | Нужно хранить публичные ключи IdP, учитывать TTL |

Этот раздел напрямую связан с темой T4 отчёта: токены, API-ключи и
SSH/deploy-ключи в CI/CD — частный случай той же проблемы аутентификации
программных компонентов без участия человека.
